M2 (temporal integrity) started: split it into four sub-checks in `ROADMAP.md` (non-monotonic timestamps, control frequency jitter, dropped frames, camera/proprio desync) since it wasn't broken down before. First one done: `src/mekiki/checks/temporal.py`'s `check_timestamp_monotonicity` — streams an episode once (doesn't materialize all frames), reports `min_delta_seconds` against a `threshold_seconds` plus which frame indices violated it, never a bare pass/fail. Tested against both a clean control (`make_clean_episode`) and precisely-injected defects (duplicate timestamp → 0.0 delta, out-of-order → negative delta, sub-threshold gap only caught with a stricter threshold), plus checked against a real `lerobot/pusht` episode (161 frames, 0 violations, ~0.1s deltas matching its 10Hz rate).

Second one done: `check_control_frequency_jitter`. Takes `nominal_hz` as a required, caller-supplied value (the dataset's own declared fps, e.g. `LeRobotInfo.fps`) rather than inferring a nominal rate from the data itself — inferring it (median delta or similar) can never catch a systematic wrong-rate error, since the episode would just look self-consistent against its own median. Threshold is a fraction of the nominal interval (default 20%), not a fixed number of seconds, since the same absolute jitter means very different things at 5Hz vs 100Hz. Tested against a clean control, a single large delay at a known magnitude, a small in-threshold wobble, a tightened threshold catching that same wobble, and — the one that actually matters — a deliberately wrong declared rate (supplying 2x the dataset's real fps) flagging every single frame, proving the "declared, not inferred" design choice actually does what it's for. Verified against the real `lerobot/pusht` episode too: correct fps (10.0) gives ~0 jitter (floating-point noise only), doubled fps flags all 160 pairs.

Third one done: `check_dropped_frames`. Same declared-`nominal_hz` approach as jitter, but a different question: not "is this delta noisy" but "is this delta big enough that a whole frame is more plausibly missing than just late" (default: 1.5x the nominal interval). Estimates how many frames are missing per gap (`round(delta / nominal_dt) - 1`), not just that a gap exists. Caught a real bug while testing it: two test functions in `test_temporal.py` accidentally shared the exact same name (`test_rejects_non_positive_nominal_hz`, one for jitter's guard and one for dropped-frames'), so the second silently shadowed the first at import time and the jitter check's own input validation was never actually being tested — the coverage report's one missing line gave it away. Renamed both to be unique; would've stayed invisible otherwise since pytest doesn't warn on duplicate names within a file, it just silently keeps the last one. Verified against real `lerobot/pusht`: clean, 0 estimated dropped frames.

Fourth and last one done: `check_camera_proprio_desync`. Returns a dict keyed by camera name (a multi-camera episode gets independent results per camera, never averaged together). The real point of this one is the `is_measured` flag on each result — `CameraFrame.timestamp_is_measured` is `False` whenever a reader assumed a camera synced to the control loop rather than actually measuring it (which, per docs/episode.md, is what `mekiki.readers.lerobot` always does right now — LeRobotDataset doesn't record per-camera timestamps separately). `n_measured_frames == 0` must never be read as "0 seconds of desync" — it means desync was never actually checked. Tested that an unmeasured frame with a deliberately huge raw timestamp gap doesn't leak into the measured stats at all. Verified against real data on both sides of the reader: `lerobot/pusht`'s one camera and all 4 of `bridge_orig_lerobot`'s cameras correctly report `is_measured=False` — the honest answer, since neither dataset's reader has anything measured to report yet.

M2 (temporal integrity) is done — all four sub-checks in `mekiki.checks.temporal`, each with a clean control, precisely-injected defects at known magnitudes, and real-data verification.

`docs/consistency.md` is now written — M3's design doc, same discipline `docs/episode.md` got before any Episode/Frame code. The load-bearing decision in it: `ActionDimSpec` never says what physical quantity an action dimension predicts (position axis? orientation? gripper? joint?), and forward integration needs exactly that, so M3 introduces a new, separate, caller-supplied `ActionTargetSpec` rather than extending the already-shipped M1 types. Also pins down: single-step integration only (multi-step rollout is a different, harder problem, explicitly out of scope), frame handling limited to "same frame" and "delta in the ee frame, rotated by current orientation" (both computable from data mekiki already has — anything else fails loudly per dimension), quaternion composition for orientation deltas (not axis-wise addition — orientation isn't Euclidean), and a `base_tolerance + rate_tolerance_per_second * dt` tolerance model where both coefficients are caller-supplied, never invented by mekiki (same "declared, not inferred" principle as `nominal_hz` in M2).

`ActionTarget`/`ActionTargetSpec` are now real code: `mekiki.checks.consistency` — `ActionTarget` (kind + end_effector/axis/joint_index depending on kind) and `validate_action_target_spec`, which enforces the one structural rule the design doc calls out: every `position_axis`/`orientation_axis` group (same kind + end_effector) must have all three of x/y/z present exactly once, since partial or duplicated axes can't be integrated as a vector. Tested against complete specs (single end-effector, bimanual — two independent groups, joints, orientation), the all-`None` degenerate case (nothing modeled, still valid), and each specific way a spec can be incomplete (missing axis named exactly in the error, duplicate axis, missing end_effector/joint_index, length mismatch). No forward-integration math yet — this is validation only, exactly the next unblocked slice per the roadmap's own breakdown.

The actual integration math is done: `predict_next_proprioception` in `mekiki.checks.consistency`, implementing every per-target-kind rule from the design doc — position (absolute needs an exact frame match, delta supports same-frame and the ee-frame rotation-by-current-orientation case), orientation (delta only, ee-frame only, composed via quaternion multiply — real Hamilton-product/exponential-map math, not axis-wise addition), gripper (absolute + normalized unit only), joint (direct or delta, no frame concept). Also tightened `validate_action_target_spec` to require a group's three axes share the same mode/frame/unit, not just be structurally complete — a real gap the previous session's validation missed. Full reasoning for both this and the orientation-frame scope narrowing (below) is in `DECISIONS.md`.

The quaternion math is hand-verified, not just "looks plausible": rotating (1,0,0) by a 90°-about-z quaternion gives (0,1,0) exactly, composing two 90°-about-z rotations gives 180° exactly ((0,0,1,0)) — both checked against hand-computed values in `tests/checks/test_consistency.py`, and the orientation-integration test reuses that same verified 90°+90°=180° case end to end. No real-data check yet for this piece specifically — that needs a real dataset with a *confirmed* delta/ee-frame action encoding to be meaningful, which is really the next task's job (the residual check, run against a real dataset's genuinely-clean episodes, where a small residual is the actual correct answer) rather than something to force artificially here.

The residual + tolerance check is done: `check_action_state_consistency` + `ToleranceModel`. Streams an episode once, forward-integrates each step via `predict_next_proprioception`, compares against what the next frame actually recorded — Euclidean distance for position, quaternion angular distance for orientation, absolute difference for gripper/joint — and reports each against `ToleranceModel`'s `base + rate*dt` per quantity. Results are a dict keyed `"position:<ee>"` / `"orientation:<ee>"` / `"gripper:<ee>"` / `"joint:<index>"`, one `ConsistencyResult` per quantity actually modeled, never averaged across quantities. Tested against a perfectly-consistent synthetic episode (0 residual everywhere), known-magnitude injected mismatches for all four quantity kinds, a case proving the `rate*dt` term actually loosens tolerance for a larger timestep (not just base), multi-step index tracking, and every "expected value missing from the next frame" raise path. 134 tests, 100% coverage on `mekiki.checks.consistency`.

**The real-data gap flagged last session is resolved — went with option (a) (reader-side, caller-supplied state mapping), since it's exactly the same pattern already used everywhere else in this project (`ActionSpaceSpec`, `ActionTargetSpec`, `nominal_hz`, `ToleranceModel`): explicit and caller-declared, never inferred.** New module `mekiki.state` (`StateField`/`StateFieldSpec`/`reconstruct_proprioception`/`reconstruct_episode_proprioception`), symmetric to `ActionTargetSpec` but mapping raw `Proprioception.extra` values into structured fields instead of mapping action dimensions to predictions. Full design in `docs/consistency.md`'s new "Getting real proprioception in" section.

Real finding while building it, caught before it became a bug: **`position_axis` reconstruction turned out to be blocked too, not just `orientation_axis`.** `Pose` bundles position and orientation as one required unit — you can't construct a valid `Pose` with only position known, and defaulting the missing orientation to identity would've been exactly the kind of fabrication this project refuses to do (and would've silently corrupted any downstream orientation-based check). So `mekiki.state` only implements `gripper` and `joint` today — both are plain scalars with no such dependency. `extra` is never modified by reconstruction, even for elements that get reconstructed — redundant, never lossy.

**First real end-to-end validation of the whole M3 pipeline, not just hand-verified math:** reconstructed `bridge_orig_lerobot`'s real gripper values (`observation.state[7]`) and ran `check_action_state_consistency` against a real episode. Result: **not** zero residual — a real 0.0→~0.85 pattern that decays smoothly over several frames right when the recorded action commands the gripper to close (frame 7 onward: action asks for 0.0, state goes 0.99→0.82→0.50→0.36→0.33→...→0.0). Checked the raw parquet directly to confirm — this is genuine WidowX gripper actuator lag (a physical gripper takes several control steps to actually close), not noise or a data bug. That's the correct, honest outcome: the check measured something real and physically meaningful, and it's a domain-appropriate `ToleranceModel` (one that knows this gripper's settling time) that decides whether that's expected or not — mekiki's job is to report the magnitude, not invent the tolerance, exactly per docs/consistency.md. 151 tests, 100% coverage across `mekiki.checks.consistency` and the new `mekiki.state`.

**Orientation encodings done (2026-09-20) — this unblocked both things the last session left parked.** New `mekiki.rotation` (quaternion math moved out of `consistency.py` so `mekiki.state` could share it; own commit) gained `OrientationEncoding` (`quaternion_xyzw` / `rotvec` / `euler` with a required, no-default scipy-style sequence — lowercase extrinsic, uppercase intrinsic) and `quaternion_from_euler`. `mekiki.state` now reconstructs `ee_poses` from three position axes plus one declared orientation encoding, refusing position-without-orientation rather than fabricating an identity orientation. `predict_next_proprioception` now supports same-frame (fixed/world-frame) orientation deltas — pre-multiply — alongside the `ee`-frame post-multiply case. Both composition orders and the Euler conversion were checked against scipy (installed temporarily, removed after — never a dependency): 4,800 random cases over all 24 valid Euler conventions and 1,000 random composition cases, all to ~3e-16; six scipy-generated golden values are pinned in `tests/test_rotation.py`.

**Real-data validation on Bridge V2 (25 episodes, 930 steps) — three findings, written up in docs/consistency.md:** (1) Position actions equal the recorded next-state minus current to 2e-9 m in the base frame; declaring `base_link` gives ~zero residual and `ee` gives ~4.5 mm, so the check does separate a right frame declaration from a wrong one. (2) That also means the action was derived from the state, so for this dataset consistency holds by construction — a zero residual means "consistent", not independently verified. Gripper, being a commanded target, is the informative contrast. (3) Orientation actions are Euler differences, so my earlier doc claim that they agree with rotation vectors "to first order" was **wrong** (true only near zero) — corrected, residual measured (~0.007 rad mean). Also: real gripper sensors read above 1.0 on 29% of frames (max +0.018), which crashed reconstruction against `Proprioception`'s strict `[0, 1]` contract; fixed at the state-reconstruction boundary (clip within 0.05, reject beyond, raw value kept in `extra`), not by loosening the core type. Five real frames are pinned in `tests/checks/test_consistency_real_bridge.py`.

**Action provenance audit (2026-09-20)** — `mekiki.checks.provenance.audit_action_provenance`, design in `docs/provenance.md`. For each action dimension it finds, from the data alone, which recorded state dimension it resembles, whether as a change or a level, at what lag, and whether it's *exactly* that quantity (identity fraction) or just correlated. Came out of the Bridge V2 finding that one action vector can be two things: derived-from-state pose dims plus a really commanded gripper. Run blind on real data it separates three cases: Bridge (pose exact at lag 0, gripper a command the sensor follows two frames late), PushT (absolute targets followed about a frame behind), xarm_lift_medium (commanded deltas at about 12x gain). Two defects found by the synthetic ground-truth tests and fixed before publishing numbers: rank correlation of a binary column is capped near 0.866 (added a tie adjustment), and actuator lag isn't misalignment (only an exact match at a non-zero lag is flagged). It proposes, never adopts: output is a hypothesis for a person to encode in a spec. 26 tests, 100% on the module.

## parked

ideas noticed in passing, outside whatever the session's actual task was. not deciding these mid-task — come back and actually think them through before acting, prune once resolved so this doesn't pile up.

- **Camera frames in real LeRobotDataset entries are video-encoded** (av1-in-mp4 in every dataset checked so far), not raw arrays in parquet. Decoding needs a real dependency (something like PyAV) that isn't installed yet. Not blocking anything else in M1 (metadata/state/action all work without it) — a deliberate addition whenever a check first needs actual pixels, not something to reach for casually.
- **RLDS-native decoding needs `tensorflow`/`tensorflow_datasets` — a dependency in the same weight class as the torch dependency this project already refuses to make core.** Full findings in `docs/rlds.md`: the format is TFRecord-wrapped TFDS serialization, nested/sequence-encoded in a way that isn't independently documented — reading it correctly without TF itself means hand-rolling a decoder with nothing to validate it against, which is a bad idea for a tool whose whole job is catching silent data corruption. Priority's settled (v2.x support went first) but not the dependency question — if/when RLDS-native gets picked up, the sane path is a `mekiki[rlds]` extra (mirroring `mekiki[coverage]`) that pulls in `tensorflow_datasets`, never core. Still not sure it's worth it at all given how much OXE data the LeRobotDataset mirrors already cover.
- **Euler-difference orientation actions are only approximated.** Real Bridge V2 orientation actions are exact differences of recorded Euler angles, not rotation vectors; reading them as rotation vectors leaves a real ~0.007 rad mean residual (~13% of the per-step motion). Doing it exactly means adding in Euler space, which needs the raw Euler triple, but `Pose` keeps only the quaternion and converting back is ambiguous across Euler branches. Needs its own design pass (probably: let `ActionTarget` name an `OrientationEncoding` and have state reconstruction keep the raw triple alongside the `Pose`), not a patch. See docs/consistency.md, "Action-side note".
- **CI actions warn about Node 20 being deprecated.** Bump the pinned `actions/*` versions in `.github/workflows` next time CI is touched, before the runners force it.
- **Provenance audit follow-ups.** Angle wrapping in Euler-difference actions makes identity fraction read a bit under 1. A corpus-style summary of it belongs with the M11 dataset audit. It also only handles one state key at a time.
- **Absolute-mode orientation action targets** are still rejected. The `OrientationEncoding` mechanism now exists (built for state), so wiring it into `ActionTarget` is straightforward — but no dataset checked so far has needed it, so it stays undone until one does.
